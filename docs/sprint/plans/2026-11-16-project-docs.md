### Task 4: Data access and atomicity (`04-data-access-and-atomicity.md`)

**Files:** Create `docs/04-data-access-and-atomicity.md`.

**Interfaces:**
- Consumes: the `03` columns (notably `tasks.version`, `outbox_jobs.*`), the `05` policies, and `AppDatabase`.
- Produces: the anchor `#atomic-operations`. Repository naming:
  - `<entity>Repository` objects in `packages/db/src/repositories/<entity>.repository.ts`
  - executing methods use verbs (`findById`, `listByProject`)
  - statement builders are suffixed `Stmt` (`insertStmt`, `updateStatusStmt`, `insertAuditStmt`)

- [ ] **Step 1: Repository conventions.**
  - `db` is always the first parameter.
  - Explain executing methods vs `Stmt` builders.
  - Ban global imports, with a short ✅/❌ example (the review lesson about the global client).
- [ ] **Step 2: The batch pattern**, worked through on `approveTask`:
  1. `loadProjectAccess`.
  2. Read the task and its status.
  3. `canApproveTask`.
  4. `assertTransitionAllowed('REVIEW','DONE','APPROVE')`.
  5. Generate IDs.
  6. Run `db.batch([updateStatusStmt(where id and version = expected), conflictGuardStmt(), insertAuditStmt, insertCommentStmt?, insertNotificationStmt…, insertOutboxStmt…])`.
  7. Map a batch error raised by the guard to `ConflictError`; rethrow any other error.
  8. After commit: `ctx.waitUntil(dispatchOutbox(ids))` and `ctx.waitUntil(publishNotifications(ids))`.

  Keep the snippet to 40 lines or fewer.

  **Why the guard statement:** a conditional `UPDATE` that matches zero rows does not error, so without a guard D1 would commit the rest of the batch. The required pattern puts `conflictGuardStmt()` **immediately after** each conditional update. It is `SELECT CASE WHEN changes() = 0 THEN json('version_conflict') END`: the malformed JSON raises an error, which aborts the batch and rolls it all back. It lives in `packages/db/src/batch.ts`, built with Drizzle's `sql` template, so the result stays typed. The service recognizes the error by the `version_conflict` marker. The M0 spike must prove both properties: a guard failure leaves zero rows written, and the marker is detectable (R5). If D1 rejects the pattern, the spike's fallback is a guard trigger on `tasks`, recorded in `11`.

- [ ] **Step 4: Rules.**
  - The pre-read happens before the batch.
  - Nothing external (Durable Object, Slack, email, R2 delete) happens before commit.
  - R2 upload ordering: put the object first, then write the DB record in a batch. If the batch fails, delete the object. Orphan sweep: R2 objects with no DB row older than 24 hours are removed by the cron.
  - The 50-query budget (R2): loaders combine reads with `db.batch`.
- [ ] **Step 5: Anti-patterns mapped to review lessons** #3, #12, and #18 from `nativedocs/09`.
